# Apple inference opportunity audit and tuning prompt

Give the following task to an agent with shell access to the target Mac. Supply the path to this checkout along with any known bracketed fields. The prompt also works with an agent that reads files directly.

> Open SKILL.md in [metal-inference checkout] and resolve all skill paths from that directory. Optimize [model and revision] on [Mac / target Apple device] using [current engine, quant, launch or local URL]. My priority is [single-user decode, prefill at specific lengths, TTFT, concurrent throughput or energy]. Preserve [quality tolerance], [context and N concurrent sequences] and [memory cap and its scope]. Deliver [analysis only / tested configuration / approved kernel or Core ML implementation]. Keep unknown inputs visible. Discover cheap facts from the host and model metadata.
>
> **A1 — Establish the control.** Inventory the machine, engine/build, quant layout, current workload, template, pins, power and memory. Check existing experiment logs. Run the fit budget. Measure warm/cold TTFT, startup, prefill and decode separately. Measure relevant bandwidth and compute, then calculate the practical ceiling and its assumptions. For a remote device distinguish measurements on that device from estimates on the Mac.
>
> **A2 — Map opportunities before choosing.** Trace both prefill and decode from server entry to device dispatch, including state and host waits. Work through every row of references/apple-opportunities.md and add candidates found in the actual code or trace. For each record phase, path or op, shape, evidence, fraction of request time, proposed change, predicted maximum gain, quality/memory risk, cost and the smallest falsifying test. Mark each item tested, rejected, inapplicable or awaiting a named measurement. A missing profiler or model is an evidence gap.
>
> **A3 — Test the most valuable candidates.** Rank by attainable improvement on the requested workload. Start with supported engine/config levers. Compare one change between flanking controls, with at least six decode samples per arm. Include concurrency, long-context KV traffic and mixed prefill/decode stalls. Log failed attempts as well as wins. After three consecutive changes inside noise, re-profile and identify what limits further gains.
>
> **A4 — Examine kernels and ANE explicitly.** For the dominant Metal dispatch, compare built-ins and fallback against a shape-specific candidate, verify numerical parity including tails, then measure full requests. For the ANE, identify a convertible partition and count boundary transfers and state costs. Compare CPU/GPU/ANE-eligible/all Core ML policies, inspect the plan, collect runtime placement evidence, and compare the whole request against native MLX or llama.cpp. Preserve candidates that require different hardware or future engine support in the opportunity table.
>
> **A5 — Qualify and hand back.** Test exact needles near half and full context, concurrent near-full requests, deterministic parity or a labelled quality evaluation, supported chat/tools/reasoning/vision, and sustained memory/thermal behavior. Pin and rebuild a winner before distributing a recipe. Start the report with metric, baseline, winner, practical ceiling and measurement method. Include ranked remaining opportunities, rejections with evidence, reproducible commands, ledger/config paths, what was unverified and final machine state. Publish only when requested.

For a fit question, use the short budget/triage route in SKILL.md. For an analysis-only request, deliver the opportunity table and proposed measurements within the authorized scope.
